# 서버 분리 — 게이트웨이(거의 안 꺼짐) / 앱(자주 재배포)

> 상태: **1단계 완료**(2026-10-08, 코드 모듈 분리·동작 동일). 2단계부터는 미완 — 아래 "남은 단계".

## 왜
앱을 자주 재배포하는데 증권사 웹소켓은 키당 1세션이라, 재시작할 때마다 연결이 끊겨 체결통보를 놓치고 평단·수량이 어긋났다.
토큰 발급(1분 1회)·호출 간격 제한도 프로세스 하나가 쥐고 있어야 안전하다. 그래서 **외부 API를 전담하는 서버를 따로 두고 거의 안 끈다.**

## 구조 (사용자 결정)
```
KIS ─REST/WS─▶ [게이트웨이] ─DB(체결 원장·잔고·분봉·주문 기록)─▶ [앱] ─WS─▶ 브라우저
                    └────────WS(시세·체결 알림)───────────────▶
```
| | 게이트웨이 | 앱 |
|---|---|---|
| 기준 | **키가 필요한 것**(KIS 키·토큰·계좌·HTS ID) | 키가 필요 없는 것 |
| 하는 일 | 외부 API 전부(REST·웹소켓), 토큰·호출 제한, 체결통보를 받아 **그대로 행으로 기록**, 주문 실행·취소, 최종 리스크 가드, 시작 시 REST 백필, 장마감 직전 미체결 전량 취소 | 전략·판단, 화면, 브라우저 웹소켓, 알림 웹훅, 종목 마스터 다운로드(공개 파일, 키 없음) |
| 시크릿 | KIS 키 등 (`application-local.yml`은 게이트웨이에만) | DB 접속 정보 + 웹훅 주소만 |
| 재배포 | 드물게, **장 마감 후에만** | 아무 때나 (웹소켓 세션이 없으니 끊김 문제 없음) |

- **웹훅은 앱이 가진다**(2026-10-08 결정). 게이트웨이가 죽었다는 알림을 하트비트를 보는 앱이 직접 보낼 수 있다. 게이트웨이의 오류·알림은 `error_log`/원장에 쌓이고 앱이 읽어 보낸다(앱이 재배포 중이면 늦게 갈 뿐 사라지지 않는다).
- 정합성이 최우선이다. 저장은 단순하게 — 체결통보는 받은 필드 그대로 한 행씩 쌓고(append-only, 컬럼 추가만 허용), 보유 수량·평단은 거기서 계산한다. 틱은 저장하지 않는다(유실돼도 무관).
- 매매 공백은 허용한다(재배포 중 판단이 멈춰도 됨). **못 받은 응답은 허용하지 않는다** — 체결통보·주문 응답이 그렇다.

## 통신 원칙
- **시세·체결 알림**: 게이트웨이 → 앱 웹소켓. 앱이 끊기면 시세는 최신 값부터 다시 받는다(재생 불필요).
  체결통보의 정본은 **DB 원장**이고 웹소켓은 빠른 알림일 뿐이다. 앱은 마지막으로 처리한 원장 ID 이후를 DB에서 읽어 따라잡는다.
- **느린 앱이 게이트웨이를 막지 않는다**: 연결마다 크기가 정해진 큐, 시세는 종목별 최신 값만 남긴다.
- **시세가 끊기면 앱은 매매 판단을 멈춘다**(오래된 가격으로 판단 금지).
- **명령(주문·취소)**: 앱 → 게이트웨이. 방식은 미정(아래 "결정할 것"). 어느 쪽이든 요청마다 ID를 두고 멱등으로 처리하며,
  **호출 전에 "보내는 중"을 먼저 기록**하고 응답이 모호하면 당일 주문조회로 확정한다. 결과를 모르는 요청은 맹목적으로 재시도하지 않는다.
- 내부 통신은 외부에 열지 않는다(같은 서버·사설망, 공유 토큰).

## 정합성 안전장치
1. 게이트웨이 시작 시 **REST 백필**(당일 주문체결내역·잔고)로 꺼져 있던 동안의 체결을 채운다. 주문번호별 "REST 누적 체결 − 웹소켓 합계"의 부족분만 보충 행으로 추가한다(체결통보에 건별 체결 번호가 없어 건별 유일 키는 못 쓴다).
2. 백필이 끝나기 전에는 새 주문을 처리하지 않는다.
3. **장 마감 직전(15:20 전) 미체결 전량 취소** 후 DB 반영, 마감 후 증권사 미체결 조회로 0건인지 대조 → 남으면 `[동기화 불일치]`. 이것이 "마감 후 게이트웨이 배포"의 전제다.
4. 하트비트(DB 마지막 수신 시각)·헬스체크, 자동 재시작. 게이트웨이는 **하나만** 뜬다(DB 잠금).
5. 증권사 값과 DB가 다르면 `[동기화 불일치]` ERROR(이미 구현, CLAUDE.md 규칙).

## 1단계 결과 (이 문서의 현재 상태)
Gradle 멀티모듈. **한 JVM·한 jar로 같이 뜨므로 배포·동작은 그대로다.** 앱이 게이트웨이를 컴파일 단계에서 못 쓰게 막는 것이 핵심이다.

| 모듈 | 내용 | 의존 |
|---|---|---|
| `common` | 증권사 계약(`BrokerClient`·모델·`FillNotice`·`Market`·`PriceTick`), 이벤트, 공용 엔티티·저장소(`Trade`·`TradeFill`·`AccountHolding`·`SymbolStrategy`·`MinuteCandle*`·`ErrorLog`), `SyncMismatchReporter` | — |
| `gateway` | `broker/kis`(클라이언트·토큰·웹소켓·체결통보), `broker/paper`, 잔고 동기화·체결 원장·체결 보충·체결 재확인, 분봉 수집, 실시간 구독 종목 | `common` |
| `app` | 전략·진입/청산/마틴게일, 화면·컨트롤러, 알림, 백테스트, 종목 마스터, 설정 | `common` (`gateway`는 **runtimeOnly** — 컴파일 의존 없음) |

경계를 이루는 계약(앱 ↔ 게이트웨이):
| 계약 | 위치 | 지금(한 JVM) | 서버가 갈라지면 |
|---|---|---|---|
| `FillProgress` (체결이 보유 현황에 반영됐나) | common | 게이트웨이 `HoldingSyncService`가 구현 | DB 원장으로 답하는 앱 구현으로 교체 |
| `MinuteCandleCollector` (분봉 수집 요청) | common | 게이트웨이 `BrokerMinuteCandleCollector` | 게이트웨이가 스스로 주기 수집, 앱은 호출하지 않음 |
| `CandleUpdated` 이벤트 (분봉 갱신 → 화면 중계) | common | 스프링 이벤트 | 게이트웨이→앱 웹소켓으로 전달 후 앱이 같은 이벤트로 재발행 |
| `FillAppliedEvent`·`TradeFilledEvent`·`HoldingsChangedEvent`·`PriceTick`·`FillNotice` | common | 스프링 이벤트 | 위와 같음 (이벤트 클래스가 곧 전송 계약) |
| `EtfRegistry` | common | 앱 `SymbolStrategyService`가 구현 | 게이트웨이도 `symbol_strategy`를 읽는 구현이 필요 |

그 밖에 이번에 끊은 직접 참조: 게이트웨이의 종목 이름 조회는 `SymbolNameLookup`(저장소 직접 읽기), 실시간 구독 종목은 `DbRealtimeSymbolSource`가 `SymbolStrategyRepository`를 직접 읽는다.

규칙: **앱 코드가 `gateway` 클래스를 부르면 빌드가 깨진다**(실제로 확인함). 새 클래스는 아래 기준으로 둔다.
- KIS와 닿거나 키가 필요하다 → `gateway`. **게이트웨이에는 전략 로직을 두지 않는다.**
- 전략·화면·알림 → `app`.
- 둘 다 쓰는 계약·엔티티·이벤트 → `common` (게이트웨이·앱 어느 쪽 구현에도 의존하지 않는다).

## 남은 단계
| 단계 | 내용 |
|---|---|
| 2 | **게이트웨이 독립 실행**: 별도 Boot 앱·설정, 스키마 소유자 정리(지금 `ddl-auto: update` — 게이트웨이 테이블은 게이트웨이만 변경), 하트비트·단일 실행 잠금, 게이트웨이→앱 이벤트 전달(웹소켓)과 앱 쪽 구현(`GatewayBrokerClient`·DB 파생 `FillProgress`), 분봉·잔고·백필을 게이트웨이 자체 스케줄로, `RiskGuard`와 `Trade` 기록 생성(주문 응답 시점)·미체결 취소(`PendingOrders`) 이동 |
| 3 | 배포 파이프라인 2개(서비스 2개·시크릿 파일은 게이트웨이만), 게이트웨이는 장 마감 후만 배포, 앱은 시크릿 없이 기동 |
| 4 | 장 마감 직전 미체결 전량 취소 + 마감 후 대조, 시작 시 백필 강화(주문번호별 누적 대조) |

2단계에서 앱이 아직 `BrokerClient`를 통해 직접 부르는 곳(전부 게이트웨이 경유로 바꿔야 한다): `quote`(진입·청산·마틴게일·수동 주문), `placeOrder`(진입·청산·마틴게일·수동·점검 실행기), `cancelOrder`(`PendingOrders`·수동 취소), `orderStatus`(`PendingOrders`·수동 취소), `holdings`·`buyingPower`·`filledPrice`(점검 실행기), `previousClose`(차트). 분봉·잔고·체결 보충은 이미 DB 경유라 게이트웨이가 쓰고 앱은 읽기만 하면 된다.

## 결정할 것
- **명령 방식**: 내부 HTTP 호출(동기 응답, 지금 코드의 `BrokerClient` 흐름과 가장 가깝다) vs DB 요청 테이블(앱이 재시작돼도 요청이 남지만 비동기·폴링 지연 0.2~0.5초). 멱등 키·"보내는 중" 선기록은 어느 쪽이든 필요하다.
- 장 마감 직전 취소 시각(제안: 15:19 시작, 15:20 단일가 전에 끝낸다).
- KIS 주문 API에 요청별 멱등 키가 있는지 — 확인 못 함. 같은 appkey로 웹소켓을 두 번째 연결하면 KIS가 어떻게 하는지도 확인 못 함.
