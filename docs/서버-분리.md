# 서버 분리 — 게이트웨이(거의 안 꺼짐) / 앱(자주 재배포)

> 상태: **구현됨**(2026-10-08) — 모듈 분리(1단계) + 해석 로직의 앱 이전·`common` 해체·게이트웨이 독립 실행·배포 파이프라인(2a~2d, 3단계 최소) + 원문 통로(한투 REST·주문·잔고·분봉·시세·체결통보를 해석 없이 전달·저장, 2026-10-08). 남은 일은 맨 아래 "남은 일". **최우선 원칙은 "게이트웨이를 다시 띄울 일을 만들지 않는다".**

## 왜
앱을 자주 재배포하는데 증권사 웹소켓은 키당 1세션이라, 재시작할 때마다 연결이 끊겨 체결통보를 놓치고 평단·수량이 어긋났다.
토큰 발급(1분 1회)·호출 간격 제한도 프로세스 하나가 쥐고 있어야 안전하다. 그래서 **외부 API를 전담하는 서버를 따로 두고 거의 안 끈다.**

## 최우선 원칙: 게이트웨이를 다시 띄울 일을 만들지 않는다 (2026-10-08)
장 마감 후라도 **웬만하면** 게이트웨이는 재배포하지 않는다. 이 서버를 따로 둔 이유가 "재시작 때마다 웹소켓이 끊겨 체결통보를 놓치는 것"이기 때문이다. 아래는 지침(CLAUDE.md)과 같은 내용이다.

1. **기록·전달·실행만 한다.** 한투에서 받은 것(REST 응답·실시간 시세·체결통보·잔고·분봉)은 **원문 그대로** 앱에 전달하거나 행으로 저장하고, 주문 실행·취소와 알림 전달만 한다. **해석 금지** — 평단·수량·손익 계산, 체결 상태 판정, 보류·쿨다운·재시도 정책, 종목 이름·전략 설정 읽기는 앱이 한다. (분리 전 이력에서 게이트웨이 쪽 파일 중 가장 자주 바뀐 게 `HoldingSyncService`(11회)·`TradeReconciler`·`HoldingSyncScheduler`처럼 해석 로직이었다.)
2. **고쳐도 되는 이유는 셋뿐**: 증권사 API 명세 변경, 게이트웨이 자체 버그, 보안. 기능·정책 변경은 앱에서 푼다. 꼭 고쳐야 하면 PR에 이유를 적고, 장중 배포 금지, 변경을 묶어 장 마감 후 한 번에.
3. **공유하는 것은 코드가 아니라 계약뿐**이다. 게이트웨이와 앱이 합의할 것은 "통로" 형식 셋 — ① 한투 REST 통로(`/api/kis/**`) ② 웹소켓 메시지 ③ 공유 DB 테이블 — 이고 **한 장**([contracts/README.md](contracts/README.md))에만 적는다. 내용(필드·응답 형식)은 한투 공식 문서([kis-api/](kis-api/))가 기준이라 계약에 옮겨 적지 않는다. 같은 모양이 양쪽에 필요하면 **각자 선언하고 테스트로 맞춘다.** 계약은 추가만 하고 삭제·변경하지 않는다. 코드 몇십 줄 중복이 게이트웨이를 다시 띄우는 비용보다 싸다.
4. **공용 모듈은 없다.** `common` 은 해체했다(2026-10-08) — 새 공용 코드 모듈을 만들지 않는다. 같은 모양이 양쪽에 필요하면 각자 선언한다.
5. **게이트웨이는 앱 소유 데이터를 읽지 않는다.** 예외는 앱이 게이트웨이용으로 일부러 쓰는 **좁은 계약 테이블 `watch_symbol(market, symbol, etf)`** 뿐이다 — 앱이 종목을 추가·삭제할 때 `symbol_strategy` 와 같은 트랜잭션에서 직접 쓰고(`symbol_strategy.watch_symbol_id` 외래키, ETF 여부도 여기가 원본), 커밋 뒤 `POST /api/watch/refresh` 로 게이트웨이에 알려 즉시 구독하게 한다. 알림이 실패해도 게이트웨이가 10초 주기로 이 테이블을 다시 읽어 맞춘다. 게이트웨이는 이 **관심종목 전체**를 구독·분봉 수집한다(앱이 꺼져 있어도 마지막 목록이 DB 에 남는다). 보유 종목은 모두 관심종목이다 — 앱이 보유 중인 종목의 삭제를 막는다. 전략 테이블 구조가 바뀌어도 게이트웨이는 영향이 없다.
6. 그래도 다시 띄워야 할 때를 대비한 안전장치는 둔다(아래 "정합성 안전장치": 시작 시 REST 백필, 장 마감 직전 미체결 취소). 원칙은 "안전장치가 있으니 자주 띄워도 된다"가 아니다.

## 구조 (사용자 결정)
```
KIS ─REST/WS─▶ [게이트웨이] ─DB(한투 원문: 체결 원장·잔고·분봉·주문)─▶ [앱] ─WS─▶ 브라우저
                    ├────WS(시세 원문·체결 알림)───────────────▶
                    └◀──HTTP(한투 REST 통로 · 주문 멱등)──────────
```
| | 게이트웨이 | 앱 |
|---|---|---|
| 기준 | **키가 필요한 것**(KIS 키·토큰·계좌·HTS ID) | 키가 필요 없는 것 |
| 하는 일 | 외부 API 전부(REST·웹소켓)를 **해석 없이 통과**시킨다 — 토큰·호출 제한·계좌번호 끼우기, 체결통보·잔고·분봉을 **원문 그대로 행으로 기록**, 주문 실행·취소(멱등), 최종 리스크 가드, 시작 시 REST 백필, 장마감 직전 미체결 전량 취소 | 전략·판단, 화면, 브라우저 웹소켓, 알림 웹훅, 종목 마스터 다운로드(공개 파일, 키 없음) |
| 시크릿 | KIS 키 등 (`application-local.yml`은 게이트웨이에만) | DB 접속 정보 + 웹훅 주소만 |
| 재배포 | 드물게, **장 마감 후에만** | 아무 때나 (웹소켓 세션이 없으니 끊김 문제 없음) |

- **웹훅은 앱이 가진다**(2026-10-08 결정). 게이트웨이가 죽었다는 알림을 하트비트를 보는 앱이 직접 보낼 수 있다. 게이트웨이의 오류·알림은 `error_log`/원장에 쌓이고 앱이 읽어 보낸다(앱이 재배포 중이면 늦게 갈 뿐 사라지지 않는다).
- 정합성이 최우선이다. 저장은 단순하게 — 체결통보는 받은 필드 그대로 한 행씩 쌓고(append-only, 컬럼 추가만 허용), 보유 수량·평단은 거기서 계산한다. 틱은 저장하지 않는다(유실돼도 무관).
- 매매 공백은 허용한다(재배포 중 판단이 멈춰도 됨). **못 받은 응답은 허용하지 않는다** — 체결통보·주문 응답이 그렇다.

## 통신 원칙
- **시세·체결 알림**: 게이트웨이 → 앱 웹소켓. 앱이 끊기면 시세는 최신 값부터 다시 받는다(재생 불필요).
  체결통보의 정본은 **DB 원장**이고 웹소켓은 빠른 알림일 뿐이다. 앱은 마지막으로 처리한 원장 ID 이후를 DB에서 읽어 따라잡는다.
- **느린 앱이 게이트웨이를 막지 않는다**: 연결마다 크기가 정해진 큐, 시세는 종목별 최신 값만 남긴다.
- **시세가 끊기면 앱은 매매 판단을 멈춘다**(오래된 가격으로 판단 금지).
- **명령·조회(앱 → 게이트웨이): HTTP 한 통로 `/api/kis/<한투 경로>`** (2026-10-08 결정). 앱이 한투 문서대로 요청을 보내면 게이트웨이는 토큰·호출 간격·우선순위(`CallPriority` 헤더)·계좌번호만 처리하고 **한투 응답을 그대로** 돌려준다. 응답 해석은 앱의 `KisBrokerClient`. 앱이 재시작돼도 게이트웨이 쪽 처리는 영향이 없다.
  - **멱등 키 필수(주문·취소)**: 요청 헤더 `X-Request-Id`. 게이트웨이는 **호출 전에 "보내는 중"을 먼저 기록**하고 응답 원문을 `kis_order` 에 저장한다. 같은 키로 다시 오면 저장된 응답을 돌려주고, "보내는 중"인 채면 409 로 앱이 당일 주문조회로 확정하게 한다(맹목적 재시도 금지). 응답을 못 받으면 앱은 **같은 키로** 다시 묻는다(새 키로 재주문 금지).
  - 앱이 못 닿는 상태(게이트웨이 점검·장애)면 앱은 매매 판단을 멈춘다.
  - 형식(경로·헤더·오류·멱등·구독 신호 `POST /api/watch/refresh`·`GET /api/health`)은 [contracts/README.md](contracts/README.md) 한 곳에만 적는다.
- **시세·체결 알림(게이트웨이 → 앱)은 웹소켓 스트림**으로 둔다(위 결정 유지). 시세는 한투 메시지 원문(`raw`)이고 체결의 정본은 DB 원장이며 스트림은 빠른 알림이다.
- 내부 통신은 외부에 열지 않는다(같은 서버·사설망에서만 바인딩, 공유 토큰 헤더).

## 정합성 안전장치
1. 게이트웨이 시작 시 **REST 백필**(당일 주문체결내역·잔고)로 꺼져 있던 동안의 체결을 채운다. 주문번호별 "REST 누적 체결 − 웹소켓 합계"의 부족분만 보충 행으로 추가한다(체결통보에 건별 체결 번호가 없어 건별 유일 키는 못 쓴다).
2. 백필이 끝나기 전에는 새 주문을 처리하지 않는다.
3. **장 마감 직전(15:20 전) 미체결 전량 취소** 후 DB 반영, 마감 후 증권사 미체결 조회로 0건인지 대조 → 남으면 `[동기화 불일치]`. 이것이 "마감 후 게이트웨이 배포"의 전제다.
4. 하트비트(DB 마지막 수신 시각)·헬스체크, 자동 재시작. 게이트웨이는 **하나만** 뜬다(DB 잠금).
5. 증권사 값과 DB가 다르면 `[동기화 불일치]` ERROR(이미 구현, CLAUDE.md 규칙).

## 구현 결과
Gradle 모듈 둘 — **서로 컴파일 의존이 없고, jar·컨테이너도 따로다.** 공유하는 건 계약뿐이다([contracts/README.md](contracts/README.md)).

| 모듈 | 내용 | 시크릿 |
|---|---|---|
| `gateway` (`com.quantlog.gateway`, 포트 8081) | KIS 토큰·호출 제한·한도 초과 재시도(`kis/KisApiClient`·`KisTokenProvider`), 한투 REST 통로(`api/KisPassthroughApi`, 계좌번호 끼우기), 주문·취소의 멱등 처리 → `kis_order`(`record/KisOrderService`), 체결통보 → `kis_broker_fill`(`record/NoticeRecorder`, 계좌 식별 칸만 비움), 잔고 응답 → `kis_balance`(`record/BalanceRecorder`), 분봉 응답 → `kis_minute_chart`(`record/CandleCollector`), 증권사 웹소켓(`kis/KisRealtimeClient`), 앱으로의 웹소켓 스트림 `/stream`(`stream/`), 단일 실행 잠금·하트비트 `gateway_instance`(`lease/`), 오류 → `error_log` | KIS 키 (`application-local.yml`) |
| `app` (`com.quantlog`, 포트 8080) | 전략·진입/청산/마틴게일·`RiskGuard`, 화면, 알림 웹훅, 종목 마스터, 백테스트, 모킹 체결(`paper/`) + **한투 해석**(`broker/`): `KisBrokerClient`(`BrokerClient` 의 한투 구현 — 요청 만들기·응답 해석·현재가 캐시), `KisBalanceParser`·`KisMinuteChartParser`·`KisFillNoticeParser`, `LatestPrices` + **게이트웨이 연결**(`gatewayclient/`): `GatewayClient`(`KisRest` 의 HTTP 구현), `GatewayStreamClient`(스트림 수신 → 시세 원문 해석해 `PriceTick`·`CandleUpdated` 재발행), `FillProjector`·`BalanceProjector`·`CandleProjector`(원장·원문 → `account_holding`·`trade`·`minute_candle`, 커서 `broker_projection_cursor`), `GatewayWatcher`(하트비트 감시·재연결 시 체결 대조·`RealtimePriceFeed`), `GatewayWatchNotifier`(감시 종목 변경 → 즉시 구독 요청), `GatewayErrorForwarder` | 없음 (DB 접속 + 웹훅 주소 + 게이트웨이 토큰) |

데이터 흐름:
- **체결**: KIS 체결통보 → 게이트웨이가 복호화해 `kis_broker_fill` 에 **원문 그대로** 한 건씩(필드 해석 없음, 계좌 식별 칸만 비움 — 해석은 앱 `KisFillNoticeParser` 가 한투 문서대로)(저장 실패 시 3회 재시도, 그래도 안 되면 ERROR 로그 — 앱의 체결 대조가 KIS 와 비교해 `[동기화 불일치]` 로 알린다) → 스트림 `fill` 알림 → 앱 `FillProjector` 가 커서 다음 행부터 체결은 `HoldingSyncService.applyFill`(보유 수량·평단, 이어서 `TradeService.onFillApplied` 가 매매 기록의 체결가·수량·체결 직전 평단), 접수 통보는 `TradeService.onOrderNotice`(미체결 확인). 알림을 놓쳐도 1초 주기로 DB 를 확인한다. **체결 내역은 `kis_broker_fill` 하나뿐이고 앱은 사본을 쓰지 않는다**(2026-10-08 — 옛 `trade_fill` 은 코드에서 지웠다). 체결 시각은 게이트웨이가 받은 시각(`received_at`)이다.
- **잔고**: 게이트웨이가 10초마다(체결 직후엔 바로) KIS 잔고조회 응답을 **원문 그대로** `kis_balance` 에 한 줄 쌓는다(한투가 오류로 답한 회차는 건너뜀) → 스트림 `balance` 알림 → 앱 `BalanceProjector` 가 가장 최근 줄이 새 것이면 `KisBalanceParser` 로 읽어 `HoldingSyncService.sync` (불일치는 `[동기화 불일치]` 로 보고 — 비교는 앱이 한다).
- **주문·조회**: 앱 `KisBrokerClient` 가 한투 문서대로 요청을 만들어 `GatewayClient` 로 `/api/kis/**` 에 보낸다(주문·취소는 요청 ID 헤더 포함) → 게이트웨이가 계좌번호를 끼워 한투에 호출하고 응답을 그대로 돌려준다. 주문·취소는 `kis_order` 에 SENDING 을 **먼저** 쓰고 응답 원문을 DONE 으로 저장, 같은 ID 재요청은 저장된 응답을 돌려주고 SENDING 인 채면 409 `RESULT_UNKNOWN` 으로 앱이 주문 상태를 조회해 확정하게 한다. 응답을 못 받는 위험(타임아웃·크래시)은 게이트웨이↔KIS 구간에서 막고, 앱↔게이트웨이 구간은 요청 ID 정도로 가볍게 둔다. 현재가는 실시간 최신가(`LatestPrices`, 10초 안)와 기억해 둔 호가 단위가 있으면 REST 를 부르지 않는다.
- **시세**: KIS 실시간 메시지 → 게이트웨이가 원문 그대로 스트림(`raw`) → 앱(`KisRealtimeTickParser`·`RealtimeCandleBuilder`)이 한투 문서대로 해석해 `PriceTick`·`CandleUpdated` 로 재발행하고 끝난 분봉을 `minute_candle` 에 저장. 느린 앱 연결은 전송 시간·버퍼 상한으로 끊고, 보내기 대기가 많으면 새 시세를 버린다.
- **분봉**: 게이트웨이가 감시 종목(`watch_symbol`)의 당일분봉조회 응답을 **원문 그대로** `kis_minute_chart` 에 쌓는다(직전과 같은 본문은 건너뜀, 하루 지난 줄은 삭제) → 앱 `CandleProjector` 가 종목별 가장 최근 줄을 `KisMinuteChartParser` 로 읽어 새 분봉만 `minute_candle` 에 넣는다.
- **감시 종목**: 앱이 `watch_symbol`(원본)과 `symbol_strategy`(FK)를 한 트랜잭션에서 쓴다(보유 중인 종목은 삭제 불가) → 커밋 뒤 `POST /api/watch/refresh` → 게이트웨이가 읽어 구독·수집. 실패해도 게이트웨이가 10초마다 다시 읽는다.
- **게이트웨이 감시**: 앱이 `gateway_instance.heartbeat_at` 이 20초 넘게 멈추면 `[게이트웨이 끊김]` ERROR(웹훅은 앱이 보낸다), 게이트웨이의 `error_log` 행도 웹훅으로 전달한다. `ws_connected_at`/인스턴스가 바뀌면(재연결·재시작) 체결 대조를 돌린다(보고만, 원장에 쓰지 않음). 계약 버전이 다르면 `[게이트웨이 계약]` ERROR.
- 게이트웨이는 `gateway_instance` 행 임대(lease)로 **하나만** 뜬다. 임대를 잃으면 프로세스를 종료한다.

규칙: 앱은 게이트웨이 클래스를 컴파일에서 볼 수 없다(모듈 의존 없음). 새 클래스는 이렇게 둔다.
- KIS 와 닿거나 키가 필요하다 → `gateway` (기록·전달·실행만. 전략·해석 금지).
- 그 밖의 전부 → `app`.

## 배포 (3단계 최소 구현)
`deploy/` — 컴포즈 서비스 `gateway`(컨테이너 `quantlog-gateway`, 호스트에 포트를 열지 않음)와 `quantlog`(앱). `deploy.sh` 가 두 jar 를 올리고 `remote-deploy.sh` 가 **앱 → 게이트웨이** 순으로 배포한다. 게이트웨이는 jar 내용(sha256)이 바뀌었을 때만, 그리고 장중(평일 08:30~15:31 KST)이 아닐 때만 배포한다(`FORCE_GATEWAY=1` 또는 워크플로 수동 실행의 `force_gateway` 로 강제, 게이트웨이가 아직 없으면 무조건). 서비스별 기동 확인·롤백. 서버 `.env` 에 `QUANTLOG_GATEWAY_TOKEN`(앱·게이트웨이 같은 값)이 필요하다 — `deploy/DEPLOY.md`.
