## 원문 통로 리뷰에서 나온 일 (PR #83·#84 리뷰, 2026-10-08)
게이트웨이가 원문만 전달하는지, 화면 기획과 어긋난 곳이 없는지 리뷰한 결과다. 화면의 실시간 표시(보유 현재가·평가손익·평단·대기열·체결 내역·차트)는 모두 이어져 있다. 게이트웨이를 고쳐야 하는 항목은 **장 마감 후 한 번에** 묶어 배포한다.

**심각도 중**
1. **체결통보 원문을 통째로 버리는 경우가 있다** — `gateway` `kis/KisFillNoticeHandler.kt` `onData`: 칸 수가 헤더 건수로 나눠떨어지지 않으면 저장하지 않고 ERROR 로그만 남긴다("유실되지 않는다" 전제 위반, 앱이 복구할 수 없음). 원인은 계좌 칸을 **칸 위치**(0·1·17번)로 가리는 방식이라 칸 배치가 바뀌면 가릴 수 없는 것. 고칠 방향: 계좌번호·HTS ID 는 게이트웨이가 아는 **값**과 같은 칸을 찾아 가리고, 나눌 수 없는 메시지도 그렇게 가린 뒤 통째로 저장한다(계좌명 칸은 위치로 가리는 수밖에 없다). 게이트웨이 수정 사유: 버그·보안.

**심각도 하**
2. **계좌번호를 끼울 TR 목록이 게이트웨이에 고정**돼 있다 — `gateway` `api/KisPassthroughApi.kt` `KisAccountTr`. 앱이 계좌가 필요한 새 TR(예: 기간별 손익)을 쓰려면 게이트웨이를 다시 띄워야 한다. 고칠 방향: 앱이 `CANO`·`ACNT_PRDT_CD` 를 빈 값으로 보내면 게이트웨이가 채운다(목록 없이). 1번과 같이 배포.
3. 게이트웨이에 남은 최소 판단 — `record/BalanceRecorder.kt`·`record/CandleCollector.kt` 의 `rt_cd` 성공 확인, 분봉 수집의 장 시간(`Market.isTradable`) 판단. 해석이라 보기 어려워 지금은 둔다. 장 시간이 바뀌면 게이트웨이를 고쳐야 한다는 것만 기억.

**리뷰 전부터 있던 것**
4. **주문 요청 ID 멱등이 실제로 쓰이지 않는다** — 앱 `app` `broker/KisBrokerClient.kt` 가 주문·취소마다 새 `X-Request-Id`(UUID)를 만들고, 응답을 못 받았을 때 같은 ID 로 다시 묻지 않는다. 게이트웨이의 409 `RESULT_UNKNOWN`·502 `PREVIOUS_FAILED` 를 처리하는 코드도 앱에 없고, 게이트웨이 타임아웃(`GatewayUnavailableException`)이면 주문이 나갔는지 모르는 채 실패로 끝난다. 계약(`docs/contracts/README.md` 멱등 절)대로 "같은 ID 로 다시 묻기 → 409 면 당일 체결조회로 확정"을 앱에 넣는다.

**염두에 둘 것 (지금은 하지 않음)**
5. **체결내역 동기화** — 원장(`kis_broker_fill`)과 KIS 당일 체결내역(`inquire-daily-ccld`)을 맞춘다. **원칙은 체결통보를 놓치지 않는 것이 현재 전제**라 "빠진 통보를 채우는 보충"이 아니라, 전제가 깨질 때를 염두에 둔 동기화로 둔다(예전 `docs/서버-분리.md` "시작 시 REST 백필" 계획을 대체). 맞출 때 다르면 `SyncMismatchReporter` 로 보고한다(CLAUDE.md 동기화 불일치 규칙). 원장은 게이트웨이가 쓰는 원문이므로 어디에 어떤 형식으로 맞춘 결과를 둘지(원장에 구분 줄을 쓸지, 앱 쪽에 둘지)는 할 때 정한다. 지금은 앱의 체결 대조(`app` `position/FillBackfillService.kt`)가 어긋남을 보고만 하고, 보유는 잔고 스냅샷이 맞춘다.

## 주문 상태 경우의 수 정립 (2026-10-07)
**배경:** 이날 익절이 10분 쿨다운에 막혀 안 나간 일(체결된 매도의 쿨다운이 새로 산 물량까지 막음)로, 매수·매도 경로마다 "미체결·체결·보유 변화"를 다루는 방식이 제각각이라는 게 드러났다. 지금은 마틴게일(틱)·청산 매도만 공용 `PendingOrders`(체결 확인까지 대기, 10초 미체결이면 취소 후 즉시 재판정)를 쓰고, 나머지는 경로별로 다르다. **모든 경우를 표로 정하고 한 규칙으로 맞춘다.**

**현재 경로별 동작 (코드 기준):**
| 경로 | 주문 후 | 미체결이면 |
|---|---|---|
| 마틴게일 틱 / 청산 매도 | `PendingOrders` 로 체결 확인까지 그 종목 판정 보류 | 10초 뒤 취소 → 다음 틱 재판정 |
| 마틴게일 폴링(실시간 끊김) | `hasUnsyncedTrade` 차단 + 실패 시 10분 쿨다운 | 취소 없음 |
| 저점 판단 진입 | `lastSignalAt` 10분 쿨다운 | 취소 없음 |
| 주기 재매수 | 보유 0주일 때만, 주기(분)마다 | 취소 없음. **보유가 아직 0이라 다음 주기에 또 주문이 나간다(미체결 주문이 쌓임)** |
| 수동 주문 | 사용자가 취소 | — |

**정해야 할 것 (경우의 수):**
1. 매수 미체결 중 보유 0 → 다음 주기 재매수·저점 진입이 또 나가도 되나? (10/7 "중복 매수 허용"과 충돌 — 미체결이 쌓이면 한꺼번에 체결될 위험)
2. 매수·매도 **미체결 취소 규칙**을 전 경로 공통으로 할지(`PendingOrders` 확대) — 타임아웃을 경로별로 다르게 둘지
3. **부분체결**: 일부만 체결된 주문을 취소하면? 남은 수량은 어떻게(보유 일부 + 취소) 판정하나. 매도 부분체결 후 남은 수량 재판정
4. 같은 종목에 **매수 대기 중 매도 신호**(또는 반대): 서로 취소하나, 막나
5. 취소 **거부**(이미 체결됐을 수 있음) 후 포기(2분) 뒤 보유 불일치를 어디서 바로잡나
6. **취소 직후 재판정**의 지정가: 매번 현재가±한 호가로 새로 잡는데, 급락/급등 중이면 계속 미체결 → 상한(재시도 횟수·가격 한도)이 필요한가
7. 실시간 끊김일 때 체결통보가 없으면 `isOrderFilled` 를 못 믿는다 → 대기 해제 기준
8. 쿨다운이 남은 곳(저점 진입 10분·마틴게일 실패 10분)을 체결 기반으로 바꿀지 유지할지

**결과물:** 이 표를 `playbook/principles.md`(원칙)와 `docs/기획서.md`에 반영하고, 정한 규칙대로 `EntryScheduler` 각 경로를 `PendingOrders` 로 맞춘다.

## 체결통보 WebSocket 실측 검증 (PR #40·#41, 2026-10-07)
**국내 모의는 실측 끝:** 체결통보는 주문 후 1~2초에 오고(REST 확인보다 8~12초 빠름), 한 주문에 접수·체결 2건이 온다. 필드 위치·접수/체결 값 의미는 [`kis-api/field-reference.md`](kis-api/field-reference.md) 3절에 확정했다(한 건 23필드, `01`=매도/`02`=매수).

**남은 실측** (서버가 이미 구독 중이라 서버를 끌 필요 없다. 서버 수동 주문 API `POST /chart/KR/005930/order`(`side`·`quantity`) + 서버 로그 `[체결통보]`, 사용자 확인 후 소량 주문):
1. **부분체결** — 수량 2주 이상 지정가 주문이 나눠 체결될 때 `CNTG_QTY` 가 건별인지 누적인지. 못 보면 DB 갱신에서는 "주문번호별로 이미 반영한 수량을 기억하고 주문수량을 넘지 않게" 막고 REST 잔고 보정에 맡긴다.
2. **취소·정정·거부 통보** — 값(`RCTF_CLS`·`RFUS_YN` 등)을 취소 주문으로 확인.
3. KIS 잔고 REST 가 한 번에 3~8초 걸린다(2026-10-06 로컬, 10-07 서버 모두 `[KIS 느린 호출]`) — 잔고 동기화 한 번이 그만큼 걸린다.

**3단계 완료 (2026-10-07):** 국내 체결 통보가 오면 `HoldingSyncService.applyFill` 이 `AccountHolding` 수량·평단을 즉시 계산해 반영한다(주문번호별 반영 수량을 기억해 중복·주문수량 초과를 막고, KIS 잔고 REST 는 정답으로 덮어쓰는 보정용). 실거래로 확인할 것: 체결 직후 `[체결통보 반영]` 로그와 이어지는 `[잔고 동기화]` 변경 내용(수량·평단 차이)이 일치하는지.

**4단계 완료 (2026-10-07):** 국내 마틴게일을 `PriceTick` 기반으로 판정한다(`MartingaleService`). 틱이 오면 DB 평단과 값싼 사전 비교 → 조건이 맞을 때만 시세·규칙·주문. 주문한 종목은 체결통보로 DB 가 반영될 때까지 "단계 진행 중", 10초 미체결이면 취소(`MartingaleScheduler`) 후 다음 틱에 바로 재판정. 체결통보를 매매 기록에도 이어 붙였다(`TradeService.onFillNotice` — 통보가 주문 응답보다 먼저 와도 체결가를 채움). 주기 재매수·저점 판단 진입은 `hasUnsyncedTrade` 차단을 뺐다. 실시간 끊김 종목의 마틴게일은 `EntryScheduler` 폴링(+`hasUnsyncedTrade`)이 계속 맡는다.

**배경:** 지금은 매수·매도·체결 알림과 오류 알림이 웹훅 URL 하나(`quantlog.notify.webhook-url`)로 한 채널에 섞여 온다. 슬랙 웹훅은 URL 하나가 채널 하나라서, 채널을 나누려면 종류마다 URL이 필요하다. 종류가 3개를 넘길 것 같아 **봇 토큰 1개 + 메시지마다 채널 지정** 방식으로 가기로 했다(채널을 늘려도 시크릿은 그대로).
**할 일:**
- `Notifier` 가 봇 토큰(`chat.postMessage`, `chat:write`)이 설정돼 있으면 채널을 지정해 보내고, 없으면 지금처럼 웹훅 URL 하나로 보낸다(설정을 안 하면 동작 그대로).
- 알림 종류를 코드에서 구분해 넘긴다(주문·체결·오류 등). 종류 → 채널, 오류는 분류 태그(`ErrorLogClassifier.category`) → 채널 매핑은 설정으로 둔다. 매핑에 없는 건 기본 채널로.
- 채널 이름·나눌 종류를 사용자와 정한다(예: 주문 / 체결 / 오류-치명 / 오류-잡음).
**사용자가 할 일:** 슬랙 앱 생성 → `chat:write` 권한 → 설치 후 봇 토큰 발급 → 채널마다 봇 초대 → 토큰을 `application-local.yml` 에만 넣고 서버에 시크릿 동기화(채팅·문서·커밋에 평문 금지).

## 증권사 API 실패 기록 — 호출 맥락 (2026-10-02, 위 "서버 오류 기록"이 로그 수준은 해결)
API 호출이 실패하면 지금은 로그 한 줄(`log.warn`)로만 남아서, 나중에 "그때 왜 안 샀지?"를 알 수 없다(재시작하면 사라진다). 실패를 DB에 기록해 화면·분석에서 볼 수 있게 한다.
기록할 것:
- 언제 — 실패 시각
- 무엇을 하려던 중이었나 — 호출 종류(시세·잔고·분봉·주문·체결가 조회 등), 종목, 요청 내용(주문이면 매수/매도·수량·지정가), 호출한 쪽(진입 스케줄러·청산 스케줄러·잔고 동기화·수동 주문)
- 왜 — KIS 응답 코드(`rt_cd`/`msg_cd`)·메시지 원문, HTTP 상태, 예외 종류(타임아웃·연결 실패 포함)
- 어떻게 처리됐나 — 재시도했는지, 쿨다운에 들어갔는지, 건너뛰었는지
구현 방향: `BrokerClient` 구현체(KIS) 한 곳에서 실패를 잡아 `api_failure` 테이블에 쌓는다(호출부마다 따로 남기지 않는다). 앱키·토큰·계좌번호는 요청 내용에 남기지 않는다. 같은 오류가 매초 반복되면 행이 폭증하므로 (종류+메시지) 기준으로 묶거나 횟수만 올린다. 오래된 행은 정리한다.

## 종목 추가 API (2026-10-02)
감시 종목은 지금 `/settings` 화면 폼(`SymbolStrategyService.add`)으로만 추가할 수 있다. 화면 없이도 추가할 수 있게 REST API(예: `POST /api/symbols` — 시장·종목 코드·이름·ETF 여부)를 만든다.
- 검증·기본값은 기존 `SymbolStrategyService.add` 를 그대로 쓴다(중복 종목·빈 값 거부, 매수 옵션은 모두 꺼진 채 시작, 간격·수량 기본값 5분·1주).
- 추가 직후 분봉 수집·차트 대상이 되므로, 종목 코드가 실제 존재하는지 시세 조회로 확인할지 정한다.
- 인증/접근 제한 방식을 정한다(지금 화면과 같은 보호 수준인지).
