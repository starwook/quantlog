## 1. 한 줄 요약

AI가 먼저 한투 모의투자 계좌에서, 검증 후 토스증권 실계좌에서 자동매매를 하고(청산은 %규칙에서 시작해 결과 피드백으로 개선), **수익률뿐 아니라 "왜 그렇게 판단했는지"까지 전부 공개**하는 웹서비스.

## 2. 배경과 목표

| 구분 | 내용 |
|---|---|
| 배경 | 투자운용사 공부 중. 배운 개념(매물대, 옵션, 채권, 금리 등)을 전략에 단계적으로 반영하고 결과를 검증하고 싶다 |
| 1차 목표 | 한투 모의투자 API로 AI 자동매매를 실행하고 수익률을 객관적으로 검증 |
| 1.5차 목표 | 검증 통과 시 토스증권 Open API로 실계좌 전환 (브로커 구현체만 교체) |
| 2차 목표 | 매매 판단 근거와 결과를 웹에 공개 (투명성이 차별점) |
| 3차 목표 | 전략을 모듈화해 새 지식(매물대·옵션·채권·금리)을 플러그인처럼 추가 |
| 비목표 (지금은 안 함) | 타인 자금 운용, 종목 추천/투자 권유 서비스 (본인 실계좌 자동매매는 목표에 포함) |

## 3. 차별점

- 대부분의 "수익률 공개"는 결과만 보여준다. 이 서비스는 **판단 로그(입력 데이터 → 판단 → 근거 → 주문 → 결과)** 를 남긴다.
- 전략 버전별 성과를 비교할 수 있어 "공부한 지식이 실제로 수익률을 개선했는가"를 증명하는 **학습 기록**이 된다.
- 손실도 그대로 공개한다. 신뢰의 핵심.

## 4. 타겟 사용자

1. **관전형 개인투자자**: 봇의 판단 과정을 보며 배우고 싶은 사람
2. **퀀트/자동매매 입문자**: 전략 구조와 검증 방식을 참고하고 싶은 사람
3. **운영자 본인**: 전략 개선을 위한 복기 도구

## 6. 매매 전략 설계

### 6.1 v1 전략 (초기)

- **청산 규칙**: 매수가 대비 **+1% 익절 / -1% 손절로 시작** (`quantlog.strategy` 설정). 매 청산은 규칙이 기계적으로 실행하되, **값 자체는 6.4의 학습 루프가 결과를 보고 +2%, +3% 등으로 조정한다**
- **시장 필터**: 당일 KOSPI 동향(예: 전일 대비 등락)을 AI 입력 데이터로 제공. 신규 진입 금지 조건은 리스크 가드가 강제 (7.2)
- **진입 규칙**: **별도 규칙 없음. AI가 시장·종목 데이터를 보고 매수 여부와 종목을 결정** (7장)

> 가정: 손절은 -1%로 익절과 대칭에서 시작한다 (익절만 +1%를 지정받아 임의로 둔 값, 바꾸려면 설정만 수정). 익절 +1%는 왕복 비용(수수료·세금) 비중이 커서 순기대값이 얇으므로, 반드시 **비용 반영 순수익**으로 평가한다 `[확인 필요: KIS 모의 수수료 설정]`.
>
> ⚠️ 검증 관점: 진입이 AI 판단이라면 성과가 "AI의 진입 실력"에서 나오는지 "청산 규칙"에서 나오는지 분리해서 봐야 한다. 그래서 **"무작위 진입 + 같은 청산 규칙"을 기준선(baseline)** 으로 두고, 가상 시뮬레이션으로 병행 계산해 AI가 이를 이기는지 비교한다. (대칭 청산은 진입이 무작위면 거래비용만큼 기대값이 마이너스)

> 참고: 워뇨띠 체결내역 분석([워뇨띠-분석.md](워뇨띠-분석.md))에서 고정 손절·익절은 발견되지 않았고(청산의 97%가 지정가, 스톱 32건), 손실 꼬리와 물타기가 특징이었다. 그래서 v1은 ±1% 대칭 + **타임스톱(5거래일 초안) + 물타기 금지**를 추가하고(→ 2026-09-30 사용자 결정으로 물타기 금지 폐기·삼성전자 마틴게일(0.5%마다 2배, 최대 5단계, 5단계 -3% 손절, 매도 후 재진입) 도입. 최신은 `playbook/principles.md`), 파라미터는 모의 로그로 스윕해 6.4의 학습 루프로 조정한다.

### 6.2 확장 로드맵 (공부 후 추가)

| 순서 | 지표/개념 | 전략에서의 역할(안) |
|---|---|---|
| 1 | 매물대 | 지지/저항 기반으로 손절·익절 폭을 고정 3%에서 동적으로 변경 |
| 2 | 금리 (기준금리, 국고채 금리) | 시장 국면(regime) 필터 |
| 3 | 채권 (금리 스프레드, 수익률곡선) | 위험선호/회피 신호 |
| 4 | 옵션 (VKOSPI, 풋/콜 비율) | 변동성·심리 필터, 포지션 크기 조절 |

### 6.3 전략 플러그인 구조

전략은 교체 가능한 단위로 만든다. 예시(개념):

```
Strategy
 ├─ evaluate(marketSnapshot, position?) → Signal(BUY | SELL | HOLD, reasons[])
 └─ version, parameters
```

- 지표/필터는 독립 모듈(`MarketFilter`, `ExitRule`, `EntryRule`)로 만들고 조합한다.
- **전략 버전**은 불변 기록으로 남기고, 거래는 항상 어떤 버전이 낸 신호인지 참조한다 → 버전별 성과 비교 가능.
- 과도한 추상화는 피한다: 처음엔 규칙 2~3개를 직접 구현하고, 4번째 규칙이 들어올 때 공통화한다.

### 6.4 학습·피드백 루프 (최종 목표: 고정 규칙이 아니라 결과로 개선하는 봇)

시작값은 익절 +1% / 손절 -1%이고, **최종 목표는 로그를 보고 +2%, +3% 등 더 수익률 높은 기준과 진입 판단을 찾아내는 것**이다. 여기서 "학습"은 모델 가중치가 바뀐다는 뜻이 아니라, **기록된 결과를 AI가 분석해 전략 버전(파라미터·프롬프트·교훈 메모)을 갱신하는 것**이다.

**1. 기록 (학습의 원료)**
- 진입 판단 전체(입력 스냅샷, AI 응답 원문), 청산 결과, 수수료·세금
- **보유 중 가격 경로**(예: 1~5분 간격 스냅샷 또는 최고가·최저가). 경로가 있어야 "+1% 대신 +2%였다면?"을 사후에 계산할 수 있다. 워뇨띠 분석에서 가장 아쉬웠던 부분이 이 경로 데이터의 부재다.

**2. 리뷰 세션 (주 1회 또는 청산 30건마다)**
- 코드가 결정론적으로 계산: 성과 요약, 익절 {0.5…5%} × 손절 {0.5…5%} × 타임스톱 격자에 같은 진입을 다시 적용한 **반사실 스윕**
- AI가 해석: 어떤 종목·시간대·시장 국면에서 지는가, 손절이 노이즈에 걸리는가, 진입 오답 패턴은 무엇인가 → **다음 버전 후보와 근거를 학습 노트로 기록**
- 학습 노트의 요약은 다음 진입 프롬프트에 주입된다 (프롬프트 길이 상한 적용)

**3. 검증·승격**
- 후보 버전은 실제 교체 전에 **shadow 모드**(같은 신호에 가상 청산 병행)로 돌린다
- 승격 조건(초안): 표본 ≥ 50건, **비용 반영 순기대값**이 현행보다 높음, 기간을 반으로 나눈 전·후반 모두 개선, 낙폭 한도 이내
- **한 번에 하나만** 바꾼다 (원인 분리). 모든 버전은 불변 기록, 과거 성과를 덮어쓰지 않는다

**4. 권한 경계**

| 구분 | 내용 |
|---|---|
| 자동 승격 허용 | 익절·손절·타임스톱 값 (범위 0.5~5%, 회당 변경폭 ≤ 0.5%p) |
| 사람 승인 필요 | 진입 프롬프트·로직 변경, 새 지표(매물대·금리 등) 추가, 범위를 벗어나는 값 |
| 학습이 절대 건드릴 수 없음 | 리스크 가드 한도, 킬스위치, 종목 유니버스, 롱 온리 |

**5. 함정과 대응**
- 과최적화: 표본이 작고 조합이 많을수록 우연히 좋은 값이 나온다 → 최소 표본, 전·후반 분할 검증, 격자 크기 제한
- 시장 국면 변화: 과거 최적값이 미래에 안 통한다 → 최근 구간 가중, 승격 후에도 shadow와 계속 비교
- 비용: +1% 익절은 왕복 비용 비중이 크다 → 항상 순수익 기준
- 목표 함수: 수익률 단독이 아니라 **순기대값/건 + 낙폭 제약**

### 6.5 원칙집 (Playbook): 사람 트레이더처럼 원칙을 기억하고 토론으로 바꾼다

봇은 "내 원칙은 이거다"를 잊지 않고 매 판단마다 꺼내 쓰는 트레이더처럼 동작해야 한다. 그래서 원칙·생각·변경 이력을 **사람이 읽고 고칠 수 있는 마크다운 파일**로 둔다 (`playbook/`, 구조는 [playbook/README.md](../playbook/README.md)).

| 파일 | 역할 |
|---|---|
| `principles.md` | 현재 유효한 원칙. **매 판단의 프롬프트에 주입**된다. 맨 위 "한눈에 보기" 표 + 구역(확정 / 임시 / 판단 습관 / 안전장치 / 토론 후보)으로 나눠 사람이 한 번에 읽도록 한다 |
| `principles-log.md` | 변경 이력 (날짜·원칙·이유·출처·결정자) |
| `journal/YYYY-MM-DD.md` | 봇의 일지: "오늘 국채금리가 급등해서 쉬기로 했다" 같은 생각과 판단 근거. 웹 화면에서도 본다 |
| `proposals/` | 봇이 학습해서 낸 원칙 변경 제안 (근거 데이터 첨부) |
| `sources/` | 사용자가 제공한 자료와 요약 |

**원칙이 바뀌는 경로**: ① 사용자가 자료·의견 제공 → 토론 → 합의 시 원칙 수정 + 로그 기록 ② 봇이 리뷰 세션(6.4)에서 제안서 작성 → 사용자 승인 ③ 수치 파라미터는 6.4의 자동 승격 범위 안에서만 자동 반영(로그 필수).
**불변**: 리스크 가드·킬스위치·롱 온리는 원칙 학습의 대상이 아니다.

**판단 흐름에서의 위치**: 진입 판단 프롬프트 = 원칙 전문 + 최근 일지 요약 + 학습 노트 요약 + 시장·종목 데이터. 응답에는 사용한 원칙 ID(예: P-020)를 함께 적게 해 **어떤 원칙 때문에 그렇게 판단했는지** 추적한다.
**데이터가 없는 원칙**(옵션·국채금리 등)은 데이터가 연결되기 전까지 "토론 대기 후보" 또는 P-022에 따라 근거로 쓰지 않는다.

**구현 현황**: `playbook/Playbook`이 원칙 읽기, 일지 기록, 제안서 작성을 제공한다. 프롬프트 주입과 원칙 ID 추적은 AI 진입 판단 루프를 만들 때 붙인다.

## 7. AI의 역할 (재검토 중, 2026-09-29)

> **열린 질문**: 지금까지 나온 진입 아이디어("오늘 -5%/-10%면 매수" 등)는 전부 고정 % 기준이라, AI 없이 코드만으로도 충분하다는 논의가 있었다. AI가 값어치를 하려면 숫자 하나로 안 되는 판단(뉴스·복수 종목 비교·매물대/옵션/금리 같은 아직 연결 안 된 데이터)이 있어야 한다. 현재 결론: **규칙 기반 v1로 먼저 갈지, 처음부터 AI 진입을 넣을지 다음 세션에서 정한다.** 아래 7.1~7.3은 "AI를 쓴다면"의 설계이고, 안 쓰기로 하면 이 장 전체가 대상에서 빠지고 6.4(학습 루프)만 "주기적 리뷰"로 남는다.

### 7.1 역할 분담 (AI를 쓰기로 할 경우)

| 단계 | 담당 | 비고 |
|---|---|---|
| 진입(매수) 여부·종목·수량 결정 | **AI (LLM)** | 시장 스냅샷, 종목 데이터, 현재 포지션을 입력으로 받음 |
| 청산(익절/손절 %) | 규칙 | 각 거래의 청산은 기계적으로 실행 (AI 개입 없음). **% 값 자체는 6.4 학습 루프가 조정** |
| 판단 근거 서술 | AI | 결정과 같은 응답에서 `reasoning` 필드로 함께 생성 |
| 주문 허용 여부 | 리스크 가드 (규칙) | AI 결정이 가드를 통과해야 주문 전송 |

### 7.2 리스크 가드 (실계좌라서 필수, AI 판단보다 우선)

AI 결정은 환각·오판 가능성이 있으므로 **가드는 AI가 우회할 수 없는 코드 레벨 규칙**으로 둔다.

- ~~1회 주문 금액 상한~~(2026-09-30 폐지, 시장별 자본 배분·하루 손실 한도가 대신함), 종목당 비중 상한, 일일 총 주문 횟수 상한
- 일일 최대 손실 도달 시 당일 신규 진입 정지
- 허용 종목 유니버스 제한 (예: KOSPI200) — AI가 임의 종목·상장폐지/거래정지 종목을 사지 못하게
- LLM 장애·타임아웃·응답 형식 오류 시 기본값은 "거래 안 함"
- 킬스위치: 수동 즉시 정지, 이상 감지 시 자동 정지
- 초기 운용 자금은 **감당 가능한 소액**으로 시작하고, 검증 후 단계적으로 확대

### 7.3 결정 로그 원칙

- LLM 호출의 **입력 프롬프트와 출력 원문을 저장** (사후 검증·재현용)
- 응답은 구조화된 JSON(`action`, `symbol`, `qty`, `confidence`, `reasoning`)으로 받고 스키마 검증 실패 시 폐기
- 모델·프롬프트 버전을 전략 버전(StrategyVersion)에 포함 → 프롬프트 수정도 새 버전으로 기록
- LLM 호출 비용/횟수 상한 설정 (장중 N분 주기)

## 8. 외부 연동

### 8.1 [1단계, 우선] 한국투자증권 (KIS Developers) 모의투자

> 문서 원문·확인된 TR ID 표: [kis-api/README.md](kis-api/README.md). 국내·미국 시세/매수가능/잔고/지정가 주문은 `broker/kis/KisMockBroker`에 구현됨 (모의 미국 주문은 지정가만 가능).

**우선 구현 대상.** 토스 Open API에는 모의투자(sandbox)가 없는 것으로 보여, 전략·AI 판단·리스크 가드를 KIS 모의계좌에서 충분히 검증한 뒤 토스로 넘어간다. 브로커를 `BrokerClient` 인터페이스로 분리해 KIS 모의 ↔ 토스 실전 전환은 구현체 교체만으로 되게 한다. 이 단계의 청산(익절/손절 %)은 **봇이 시세를 감시하다 직접 주문**한다(KIS 모의의 조건주문 지원 여부는 `[확인 필요]`, 토스 OCO는 2단계에서 검토).

- 용도: 시세 조회, 잔고, 주문, 체결 조회
- 인증: appkey/appsecret → 접근 토큰 (만료 주기 있음, 자동 갱신 필요) `[확인 필요]`
- 제약: 모의투자 서버의 호출 빈도 제한, 지원 종목/기능 범위, 모의 체결 방식(실제 호가 대비 체결 현실성) `[확인 필요]`
- 시크릿(appkey, 계좌번호 등)은 코드/로그/문서에 평문 금지 → 환경변수 또는 gitignore된 설정으로만 관리

### 8.2 [2단계] 토스증권 (모의 검증 통과 후 실계좌 전환)

**모의 검증 통과 후 이 API로 실계좌 매매.** 아래는 미리 조사해 둔 내용이며 1단계 구현에는 필요 없다. (v0.1에서 "공개 API가 없을 수 있다"고 가정했으나, 조사 결과 **토스증권 Open API가 2026-05 사전신청 후 2026-08 정식 출시**된 것을 확인했다. [공식 개발자센터](https://developers.tossinvest.com), [출시 기사](https://en.sedaily.com/finance/2026/08/13/toss-securities-launches-open-api-for-trading-via-chatgpt))

**확인된 사양** (원문: [toss-api/](toss-api/README.md), 2026-09-25 저장)
- 인증: OAuth2 Client Credentials → access token. 계좌·자산·주문 API는 `X-Tossinvest-Account` 헤더 필수
- 엔드포인트: REST `https://openapi.tossinvest.com`, WebSocket `wss://openapi-ws.tossinvest.com/ws/v1` (계정당 동시 연결 최대 2개)
- 범위: 국내(KRX)·미국 시세/호가/체결, 종목정보, 계좌·보유종목, 주문 생성/수정/취소/조회, 실시간 tick/호가/주문 이벤트
- **조건주문: SINGLE / OCO / OTO 지원** → 매수 체결 후 **OCO(익절/손절 현재 규칙값)** 를 걸면 청산을 토스 서버에 위임 가능. 봇이 죽어도 청산이 유지된다는 점이 실계좌에서 큰 장점. 단 OCO·OTO는 종목당 1개, 감시 장은 "장 상관없이"로 고정 (FAQ)
- **주문 멱등성**: `clientOrderId`로 중복 주문 방지 (내용이 다르면 `idempotency-key-conflict`)
- **허용 IP 등록 필수**: 미등록 IP는 403. 공인 IP가 바뀌는 환경이면 차단됨(FAQ). 고정 IP 확보 필요 → 2단계 시점의 배포 환경 계획에 영향 (12장)
- Rate limit: ORDER 초당 10회, CONDITIONAL_ORDER 5회, ACCOUNT 1회, MARKET_DATA 15회 등 (그룹별, 응답 헤더 `X-RateLimit-*`로 확인). LLM 판단 주기 대비 충분
- 매수·매도 건수 한도는 별도로 없음 (FAQ)

**아직 확인되지 않은 것** `[확인 필요]`
- **모의투자/샌드박스**: 문서 전체에서 언급 없음 → **없는 것으로 가정**. 그래서 KIS 모의를 1단계로 둔다
- 약관상 체결·계좌 데이터의 웹 공개 게시 가능 여부 (웹 공개 서비스와 직결)

**설계 반영**
- `BrokerClient` 인터페이스 + `TossBroker` 구현체 (KIS 모의 구현체는 1단계에서 먼저 만든다)
- 청산은 매수 체결 확인 후 OCO 조건주문 등록 방식을 우선 검토 (봇 장애 시에도 손절 유지)
- 토큰 만료 자동 갱신, 주문 멱등성(중복 주문 방지), 주문 후 체결 확인 폴링/WebSocket 이벤트 처리
- 시크릿(client id/secret, 계좌 헤더 값)은 환경변수·gitignore 설정으로만 관리, 로그 마스킹

## 9. 수익률 검증 방법론

"검증"의 신뢰도가 이 서비스의 핵심이므로 기준을 미리 고정한다.

**측정 지표**
- 누적/일간 수익률, 벤치마크(KOSPI) 대비 초과수익
- 승률, 평균 이익/평균 손실(손익비), 기대값(거래당)
- MDD(최대 낙폭), 변동성, 샤프지수(표본 충분해진 후)
- 거래 횟수, 평균 보유기간

**신뢰도 확보 원칙**
1. **비용 반영**: 수수료·거래세를 모두 차감한 순수익률로 표시 `[확인 필요: 현재 요율]`
2. **최소 표본**: 거래 수십 건 미만의 수익률은 "통계적으로 의미 없음" 경고 표시
3. **사후 수정 금지**: 전략 변경은 새 버전으로 기록, 과거 성과를 덮어쓰지 않는다
4. **가상 시뮬레이션과 실계좌 분리 표기**: 기준선(무작위 진입) 등 가상 계산은 슬리피지가 과소 반영됨을 병기
5. **기준선 비교**: (a) KOSPI 보유, (b) 무작위 진입 + 같은 청산 규칙, 와 항상 나란히 표시
6. **백테스트 병행 (2단계)**: 과거 데이터 백테스트는 과최적화 위험이 있으므로 "참고용"으로 분리 표기

## 11. 시스템 아키텍처

### 11.1 기술 스택 (기본값 적용, 아래 결정 필요 항목은 12장)

| 영역 | 선택 |
|---|---|
| 언어/프레임워크 | Kotlin + Spring Boot (버전은 기존 프로젝트와 통일: Kotlin 1.9.25 / Spring Boot 3.2.4 — 다른 버전 필요 시 확인). 봇과 웹서비스를 한 코드베이스로 운영, Python 불필요 |
| 영속성 | JPA + MySQL |
| 빌드/린트 | Gradle + ktlint |
| 스케줄링 | Spring `@Scheduled` (장 시간대 주기 실행) |

| LLM | Claude API (코멘터리 생성) |

### 11.2 패키지 구조 (도메인 기준)

```
com.example.<project>
 ├─ trading/      전략 실행 오케스트레이션, 주문, 리스크 가드
 ├─ strategy/     Strategy, EntryRule, ExitRule, MarketFilter, 버전 관리
 ├─ broker/       BrokerClient 인터페이스, KisMockBroker(1단계), TossBroker(2단계)
 ├─ market/       시세·지수 스냅샷, KOSPI 동향
 ├─ decision/     판단 로그(입력/결과/사유), AI 코멘터리
 ├─ position/     보유/체결/거래 내역
 ├─ performance/  수익률·MDD 등 성과 집계
 └─ home/         대시보드처럼 여러 도메인을 조합하는 화면
```

각 패키지 안에 Controller/Service/Repository/Entity를 함께 둔다. 도메인 지식은 해당 도메인이 소유한다 (예: 손절/익절 판정은 `strategy`의 ExitRule이, 수익률 계산은 `performance`가 소유).

### 11.3 매매 사이클 흐름

```
[스케줄러: 장중 N분마다]
   → market: 지수/시세 스냅샷 수집
   → strategy: 시장 필터 → 진입/청산 평가 → Signal
   → decision: 판단 로그 저장 (입력 스냅샷 + 신호 + 규칙 사유)
   → trading: 리스크 가드 통과 여부 확인
   → broker: 주문 전송 → 체결 확인
   → position/performance: 반영
   → decision: AI 코멘터리 비동기 생성·저장 (주문 경로를 막지 않음)
```

핵심: **AI 코멘터리 생성은 주문 경로와 분리**한다. LLM 지연·장애가 매매에 영향을 주면 안 된다.

### 11.4 주요 엔티티 (초안)

## 12. 미결 사항 (결정이 필요한 질문)

해결됨: 브로커 순서(KIS 모의 → 토스 실계좌), 감시 종목·자본 배분·일일 손실 한도(위 표). 보류: 공개 범위·법률(10장).

1. **진입에 AI가 필요한가**: 규칙 기반 v1로 갈지, AI 진입 판단을 넣을지 (7장 열린 질문, 다음 세션 최우선 결정 사항)
2. **정확한 진입 규칙 수치**: "몇 % 빠지면 매수"의 구체적인 숫자 (규칙 기반으로 갈 경우)
3. **동시 청산 주문 처리**: KIS 모의 주문 API에서 OCO(하나 체결 시 나머지 자동 취소) 지원 여부를 문서에서 확인 못 함 → 지금은 "체결 후 별도 감시 프로세스가 트리거될 때만 청산 주문 1건을 낸다" 방식으로 우회 (2026-09-29 테스트로 확인, 8.1 참고)
4. **클라우드 배포**: 모의투자 봇은 Oracle Cloud(Docker, 8080)에 배포됨 (2026-09-29, `deploy/DEPLOY.md`). 남은 것: 2단계(토스증권 실계좌) 배포 시점, 토스 API 허용 IP 등록을 위한 서버 고정 IP 확인
5. **학습 루프 승인 범위**: 6.4에서 익절/손절 값의 자동 승격을 허용하는 범위(0.5~5%, 회당 0.5%p 이내)와 최소 표본(50건)이 적절한가?
6. **모의 → 실전 전환 기준**: 모의에서 어떤 조건(기간, 거래 수, 기준선 대비 성과)을 통과하면 토스 실계좌로 넘어갈 것인가?
7. **프론트엔드**: Thymeleaf 서버 렌더링으로 충분한가, 별도 SPA가 필요한가?
8. **약관**: KIS·토스 각각 체결·계좌 데이터를 웹에 공개 게시해도 되는가? (웹 공개 전 필수)

## 15. 성공 지표

- **기술**: 4주 연속 무중단 자동 실행, 주문 오류율 < 1%, 모든 거래에 판단 로그 100% 연결
- **검증**: 전략이 기준선(KOSPI, 무작위 진입) 대비 초과수익을 내는지 통계적으로 판정 (못 이겨도 "못 이겼다"를 공개하는 것이 성공)
- **서비스**: 공개 후 주간 방문자, 판단 상세 페이지 조회율, 체류시간
- **학습**: 전략 확장(매물대 등) 전/후 성과 비교 자료 확보
